# Learning animation maker (strict edition 3)

Goal: a single HTML learning product from which a learner can pass the exam WITHOUT reading anything else. It has four modes that share one data set: ANIMATION mode (narrated story), GAME mode (arcade decks and sandboxes), PATHWAY mode (summaries, then games passed as exams, then the checkpoint, chapter by chapter) and EXAM mode (full 2-hour and 4-hour mock exams). Two always-available tools sit beside the modes: a DOCUMENTATION page (text only, section 6b) and VOICE SETTINGS (section 11b). Everything wears ONE gamified visual identity (section 4b): deep violet worlds, cream text, hot pink / lime / cyan / yellow accents, rounded display font, chunky buttons, XP, levels and chapter badges. Every rule and formula is explained in plain words first (section 6c). Nothing in the source is skipped, nothing is wrong, nothing overlaps, nothing is hard to read, nothing flashes by too fast. This is a long job: expect hundreds of scenes. Never ship a chapter that has not passed every gate in section 12. If time or context runs short, ship fewer chapters at full quality, never more chapters at lower quality, and write a HANDOFF.md.

## 0. Ask / decide first, and definition of done
Ask (or, if unattended, pick defaults and state them): subject, exam style (QCM/open/situation/code), language, aspect ratio (default 16:9 wide plus phone-tall layout), whether neural TTS is wanted, exam duration(s).

Done means ALL of:
1. Every item of the content inventory (section 1) is covered by a scene AND appears in the notes panel/cheatsheet AND is tested by at least one checkpoint question AND, when it is a skill or a decision, trained by a game or sandbox.
2. Zero runtime errors in wide and tall mode.
3. Zero overlaps, clipped text, touching boxes, text over art, elements outside the safe area, in wide AND tall, verified by screenshots you actually looked at plus the automated audit.
4. Every caption is readable at normal speed (section 5); no flash lasts under 1.2 s.
5. Readability gate passed (section 4): the automated contrast audit reports zero issues on the stage AND on every DOM overlay (start, menu, pathway, games, exams), wide and tall.
6. Facts and numbers match the source; every invented example is labelled 'example' on screen.
7. Pathway mode (section 9) and both mock exams (section 10) work end to end, and their tests pass.
8. The visual identity of section 4b is applied to the stage, the shell and EVERY overlay (tokens, fonts, chunky buttons, XP and level pill, chapter segments); no leftover muted navy/grey UI.
9. The documentation page (section 6b) exists, is text only, contains every note of every chapter, and its test passes.
10. Voice settings (section 11b) work: voice, speed, pitch, volume, test, presets, saved, used by every spoken line; their test passes.
11. Every rule and formula (notes and formula slide lines) has a plain-words explanation shown first (section 6c) and the plain-words gate passes.
12. Delivered: artifact + standalone HTML + zip of the project source + HANDOFF.md.

## 1. Content inventory: use 100% of the documents (before any code)
Read ALL source files completely (slides, PDFs, notes, labs, TDs/TPs, exercises, past papers, review questions). Extract the juice of every document: nothing useful may be overlooked or wasted. Specifically:
- Every question, exercise, warm-up, review Q&A and past-paper item in a lecture, lab or TD is an asset: it becomes a checkpoint question, an exam question, a game round or a sandbox mission. This includes the FIRST exercise of each lab/TP/TD, which is usually a situation question (a scenario with context, data and linked questions): use each one as a situation question in the mock exams and the checkpoints.
- Every niche or hidden concept, side remark, 'remember' box, trap, counter-example, edge case, unit, threshold, number, naming convention, and every situation or trap question shown in a lab, lecture or TD must be taken into consideration and added where useful. Mentioned-only concepts count: the exam may ask about anything demonstrated or mentioned. Never overlook potentially useful data.
- When the source gives a worked solution, reproduce its answer and deepen the explanation. When it gives none, derive the answer only from the documents and label it 'derived'.
- Keep a coverage ledger: one row per atomic item (definition, term, list item, syntax/command, formula, number/threshold, example, comparison axis, algorithm step, exercise plus its solution, review Q&A, warning, trap). Columns: id, item, source location, scene(s), notes entry, checkpoint question(s), game/sandbox, mock-exam question(s). After writing, re-diff against the source: any row without a scene, a question and (when trainable) a game is a bug; any source document that yielded fewer assets than it could is a bug. State in the handoff which documents were fully mined.
- Match checkpoints and mock exams to the exam format. Exercises and mock exams from the source are animated step by step with the solution, not merely stated.

## 2. Story and variety
One world and tone (story/documentary), a mascot host, a distinct deep violet-family tint per chapter (indigo, plum, ink blue, berry, teal, amber-brown, royal violet, forest: hue-shifted darks, section 4b), a stable accent colour per concept across the whole film. Scene types keep changing: cards, definitions, versus tables, code walkthroughs, flows/packets, bins and tokens, grids, timelines, labs (command box + data panel), quizzes. No static engineering diagram: every diagram builds piece by piece, with motion that explains the mechanism (data flows, counters tick, rings highlight, things dim). Metaphors come from the subject's own world (real units, vocabulary, conventions). A scene = one idea, 15-40 s, 3-6 beats, one caption per beat.

## 3. Architecture
- Source in src/*.js, one file per chapter (split ch##_b.js, ch##_c.js when large), concatenated by build.py into ONE self-contained HTML (fonts inlined, no network). Each chapter file is an IIFE. Overlays (arcade, pathway, exam, docs, voice, progress) are separate files with their own DOM and CSS. Engine files: core, xp (XP, levels, segments, confetti, scene cuts), kit, shell, checkpoint, arcade, pathway, voice, docs, exam, then chapters, games, exam data, plain (generated), boot. A file that is loaded before the DOM helper h exists must call it lazily (h=(...a)=>ML.h(...a)).
- Stage: SVG with two viewBoxes: wide 178x100 (safe area x12-166, y23.5-95, banner on top) and tall 100x125 (x6-94, y24-106). Helper X(wide,tall) selects per mode; WIDE() tests the mode. EVERY scene is designed for both; never reuse wide numbers for tall.
- Engine contract: scene(chapter,durMs,bgKey,run(s),{notes,notesAt,quiet,manual,title,kind}); node API add(svg,x,y,{raw,o,sc,z}), pop/out/fade/to/pls/shake/txt/fill; scene API at(t,fn), say(t,text), sfx(t,name), tag(txt,col,fg,x,y,t0,t1,{raw,sz}). Each scene carries notes (cheatsheet entries [kind,title,body,code,plain], kinds concept/syntax/rule/trap/formula; plain is the section 6c explanation), a human title and a kind (card/recap/play/check). Pathway slides and indexes are generated from these, so the notes are the single source of truth for summaries.
- Templates make most scenes DATA: tCards (<=3 items per page wide, 2 tall, auto-paginates), tDefine (term+definition+example+demo), tVs (<=3 rows per page), tCode (command box + token walkthrough), tFormula (lines, each with an optional plain caption; pages are packed by measured height), recapScene, checkpointScene, quizScene, playScene. Custom code only for genuine mechanisms.
- Layout kit with MEASURED widths: text-width function per font class; pills/chips with real widths; JSON/code box returning line y positions plus ring/block highlighters; tables (y0 is the TOP edge); bin+token sets; arrow chains; wrapping flow-pill rows. Never guess a width: compute it and shrink the font until it fits.
- Engine rules that bit us: raw nodes added at (0,0) that hold absolute geometry (arrows, lines) must pop by opacity only; never out() a node while a position to() is mid-flight; never declare a local const T (shadows the text helper); a plan variable named P shadows the path helper P() (name it Q); rect offsets are top-left relative so centre a box with -h/2; scene indices differ between wide and tall (pagination), so list indices per mode; boot code must run whether or not DOMContentLoaded already fired (if document.readyState!=='loading' call boot at once), because an artifact wrapper may run the script late; a label pill that straddles a box's top edge needs the first text row pushed down so they never touch (tall mode).
- Scene titles: generate a stable key per scene (hash of its text plus occurrence number) mapped to a title table produced by a script; re-run the script after any content edit (empty the table first so stale titles cannot survive).

## 4. Readability standards (ADHD-friendly) and the hard contrast rule
- NEVER ship unreadable or hard-to-read text and colour combinations (pale text on a cream/light box, white on a mid-tone pink, grey on dark, text over art, thin text on busy backgrounds). This applies to the stage AND every DOM overlay, in every state (hover, selected, right, wrong, disabled, locked, banner, chip, tag, button).
- Stage: cream text (#FFF7E6) on deep violet boxes only, never dark text on the stage background; bold labels use the rounded display face; no heavy black fonts; a stroke is allowed only on large display headings (start title), never on body text, captions or tags. Body text >= 3.6 units wide / 3.3 tall; mono >= 3.0 / 2.7; captions and tags larger. Contrast >= 7:1 against its box.
- DOM overlays: contrast >= 4.5:1 for text under 18.6px (under 14px if bold), >= 3:1 for large text; no opacity tricks that push contrast below that; never convey meaning by colour alone (add a word or symbol: 'correct', 'your choice', tick/cross). Buttons: cream fill with dark ink text (about 15:1); primary = hot pink #FF3D8B with DARK ink text #1A1033 (about 5:1); success = lime #B6FF3B with dark text; error = coral #FF6B7A with dark text; disabled = #3A2E66 with #D2C8F0. Never white text on a bright accent (white on #FF3D8B is only 3.4:1) and never bright text on a bright fill. Do not put a background transition on buttons: an audit taken mid-fade reports false failures.
- CSS hygiene: prefix every new UI class (ex-, pw-, ar-) and never reuse short global class names (.b .t .k); a clash silently restyles the new component (a cream box with pale text happened exactly this way). Give every component its own background AND text colour pair explicitly. Sticky overlay headers must be opaque.
- Automated gate (mandatory, wide and tall): a script opens every overlay state (start, menu, pathway map/chapter/slide/checkpoint, every game and sandbox in play and exam state, every exam screen before and after checking, index, results, documentation, voice, progress), walks all text nodes, computes the effective foreground over the composited background (include alpha layers and the overlay base colour) and fails on anything under the thresholds. Measure each wrapped text line's own rectangle (ignore rectangles narrower than about 10px, which are trailing spaces, and rectangles with almost no ink) and take the worst line; measuring the union box of wrapped text picks up neighbouring colours and gives false failures. Zero issues required. Then LOOK at screenshots anyway.
- Stage spacing: gaps >= 3 units between elements, boxes never touch, nothing within 3 units of the safe-area edge, one focal group per beat; prefer fewer, larger elements. One 'slot tag' position (centre x, y=27) for the current key phrase; one tag at a time; fade the previous before the next; content starts below y=34.
- Pause overlay and controls live OUTSIDE the stage so a stage screenshot is clean. Right-side notes panel (definition/syntax/recap/example/formula entries added as each concept appears), manual Next-chapter button.

## 4b. Visual identity: the gamified "arcade violet" look (default for every product)
Muted navy or grey UIs are rejected. Every product uses this identity (it is the NoSQL-story look) for the stage, the shell and all overlays.
- Tokens (define once in CSS :root AND in the stage colour table ML.C, reuse everywhere; no stray hex values in chapter files, use C.name): bg #0D0722, tint (page glow, per chapter) mix(chapter bg, accent, .3), panel #1C1146, panel2 #281A5C, line #4B3A96, text/cream #FFF7E6, muted #CBBFEA, dark ink #1A1033; accents pink #FF3D8B, lime #B6FF3B, cyan #2DE2FF, yellow #FFD23F, orange #FF8A2B (stage #FF9A45), mint #35E8A6, sky #4FC3FF, lilac #B79CFF, coral #FF6B7A, purple #7A3CFF. Semantic roles stay fixed across the whole product (for example data = sky, cost = coral, gradient/step = orange, probability = mint, distribution = cyan, hyperparameter = yellow, model = lilac, warning/trap = pink).
- Fonts (inlined base64 woff2, no network): body Nunito 700 (bold 900), display Fredoka 600 for titles, tags, bold labels, buttons and quiz questions, JetBrains Mono 500/700 for code and numbers. Get the files with `npm pack @fontsource/nunito @fontsource/fredoka @fontsource/jetbrains-mono` (files/<name>-latin-<weight>-normal.woff2). ALWAYS add a subset of DejaVu (Latin, Greek, math operators, arrows, sub/superscripts) as the per-glyph fallback family, because the rounded fonts have no theta, sigma, arrows, minus or script digits: font stacks are "'ML Sans','ML Sym',sans-serif", "'ML Display','ML Sym',sans-serif", "'ML Mono','ML SymMono',monospace". One helper builds the stack from (font, weight) and is used by BOTH the SVG text creator and the canvas text measurer, so measured widths always match what is drawn (weight >= 700 = display face).
- Shell: page background radial-gradient(tint, bg), changing with the chapter; cream chunky buttons (2px dark border, radius 12, hard 0 3px 0 shadow, lift on hover, press down 3px on click), pink primary, lime for the on state; panels radius 16-18 with a 2px cream-at-16% border; tags are pills; notes use a coloured left border per kind (concept cyan, syntax lime, rule yellow, trap pink, formula orange); the stage has a 3px dark ring plus a faint cream ring and a soft shadow (use box-shadow, not border, so the viewBox mapping stays exact).
- Stage world per chapter: radial gradient from a tinted centre to the chapter's dark edge (keep the glow subtle, about 9% accent, or lilac text on a teal glow drops under 4.5:1), 12-16 soft decorative shapes (circles, rounded squares, stars) at about 13% opacity in the palette, static in QA mode, a lime progress line at the bottom, mascot with a dark screen face, cyan eyes, lime smile, pink antenna ball and a gentle bob (no bob in QA mode).
- Gamification (always on, never blocking): (1) XP pill and level in the top row, with a bar and a bump animation; click opens a progress panel with level, how XP is earned and chapter badges; (2) XP is awarded ONCE per achievement key (ML.xp.once(key,n)) so replaying cannot farm points: first view of a scene 2, first-try correct answer 10, card sorted 5, each game star 20, chapter checkpoint 100, each 25% of a mock exam 50; levels every 400 XP with names (Rookie ... Legend); (3) chapter segments (one per chapter, filled by scenes seen, click to jump); (4) confetti and a toast on level-up, checkpoint pass, 3-star game, exam >= 75%; (5) scene entrance cuts (zoom, wipe, drop, spin) of about 0.45 s; (6) floating +XP text. Every animation is disabled in QA mode (ML.qa) and under prefers-reduced-motion, and nothing flashes more than once. On a phone keep the top bar to two rows (buttons, then chapter segments with the XP pill).
- Retrofit an existing product: remap hex values through one dictionary (old to new) in one script, rewrite the CSS file from the tokens, swap the font build, change bgFor, add xp.js, then re-run ALL gates (contrast and overlap change because font widths and colours change).

## 5. Timing standards
- readMs = clamp(900+46*chars, 1700, 7500). Use plan(steps) with steps=[caption,minHoldMs]: it places each caption >= previous + readMs + 600 so the scene clock never stalls, and returns at[], dur, say(s). Scene dur = last event + hold + ~2.8 s tail. Put long choreography INSIDE a beat's min hold so the caption never moves on before the animation ends.
- Tweens run in real time from creation (delay); s.at/say run on the scene clock, which stalls only when a caption arrives before the previous one's read time. Budget the sum of stagger delays inside each beat's hold.
- No flashing/strobing; pops 0.25-0.45 s; counters tick at most 6/s; every new element stays >= 1.2 s before moving or fading unless it is a transient.
- Narration: the full sentence is spoken before the next beat starts, with a pause. Spoken text uses words, not symbols a TTS mispronounces (arrows, dollar signs, dashes); the screen may use symbols. A caption is also the subtitle, so keep it short enough for its box (at most two to three lines on a phone).

## 6. Learning aids
Recap per chapter (<=6 bullets, each a real takeaway). Checkpoint per chapter covering EVERY inventory row of that chapter: answer-position rotation, plausible distractors, explanations that teach (section 7); the spoken question count equals the real count. Cheatsheet toggle with all syntax/definitions/numbers. Speed-round quiz for the finale. 'Example' label on invented numbers. Exam traps called out as warnings. Lecture/source tags on every chapter and every game.

## 6b. Documentation page (mandatory, text only)
A page reachable from the top bar and the start screen that holds ONLY text: no animation, no stage. It is generated from the same data as the notes and pathway slides (so it cannot drift): per chapter the hook, the goals, then every note grouped as key ideas, formulas, rules, syntax and exam traps (deduplicated by title, with code in mono), then the recap. Every rule and formula entry starts with its plain-words box (section 6c), the exact form second. Views: By chapter, All formulas (in plain words), All rules (in plain words), All exam traps. Features: a search box that filters entries live (also over the plain text, with a 'nothing matches' message), chapter shortcut buttons, an entry count, 'Copy as text' (clipboard with a fallback that selects a text area; the copied text puts the plain sentence first), derived or invented-data chapters labelled, readable on phone width (no horizontal scroll), contrast >= 4.5:1. Test (wide and tall): number of chapter sections equals the number of chapters, entry count equals the deduplicated note count, search 'x' shows only entries containing x, each view lists only its kind, no horizontal overflow.

## 6c. Plain-words rule for every rule and formula (mandatory)
Maths intimidates learners, so every rule and every formula carries a short plain-language explanation of what it is for and when to use it, with no maths notation (no Greek letters, sums, powers). Notes get it in a 5th element (<= 230 characters), formula slide lines in `plain` (<= 105 characters; legend lines <= 75). Show it FIRST, in a highlighted "In plain words" box, with the exact formula second and smaller (notes panel, cheatsheet, pathway slides, documentation page), and put a muted one-sentence caption under each formula on the stage; the narration speaks the plain sentence instead of reading the symbols. Keep the texts in one data file (key -> text, keys like n|chapter|note title and l|chapter|spec index|line index) and generate the loader (plain.js, loaded after the chapters, before boot) with a script; the texts may be drafted in parallel by sub-agents from a dump of the items, then validated (all keys present, length limits, no maths symbols); add a gate that fails when any rule/formula note or formula line lacks one or contains maths symbols.

## 7. Depth of explanations (never shallow)
Every answer explanation (checkpoint, game, exam) says: what the question tests and which words in the statement point to it (intent); the reasoning step by step that the learner can replay (path); the answer; why EACH wrong option fails and which misconception it stands for; how to recognise the type next time and what changes if the numbers change; where to revise (chapter, slide, lab). One-line explanations are not acceptable except for pure recall. Calculations show formula, substitution with units, rounding rule (round down for 'how many fit', up for 'on which day is the limit passed') and a sanity check.

## 8. Game mode vs animation mode: sandboxes, arcade games, game-based full coverage
Animation mode transmits and shows; game mode makes the learner decide, predict and be corrected. Use both: every concept is shown (animation), summarised (pathway slide) and trained (game).
How to translate a lesson into a game:
1. Classify the lesson content: (a) discrimination knowledge (which pattern/tool/choice fits this situation) becomes a CLASSIFICATION DECK: cards of real situations dropped into 2-5 buckets, immediate feedback with the reason, replay of missed cards, a perfect round required for mastery; (b) quantitative or structural knowledge (sizes, costs, counts, hierarchies, mechanisms) becomes a SANDBOX: sliders and inputs on real source numbers, live computed results, presets that reproduce the source's worked exercises, a 'make it worse' preset, then a MISSION EXAM; (c) procedures and syntax become WRITE-AND-CHECK tasks with a real checker (parser, comparator, emulator); (d) traps become 'spot the bug' or 'same or different' rounds.
2. Every game teaches part or all of a lesson on purpose: its blurb states which lecture/lab it covers and what the learner will be able to decide afterwards. A game that maps to no inventory row is decoration: cut it.
3. Sandbox exam rules: numeric and pick questions whose answers are computed from the SAME functions the sandbox uses (no hand-typed answers that can drift); a hint after the first wrong try, the answer with its reason after the second, the question re-queued once; stars by the share answered correctly the first time (3 stars = all first time); mastery = every question answered correctly.
4. Deck rules: balanced buckets, answer-position rotation, a 'why' on every card, no card solvable by surface wording, a perfect round for mastery.
5. Full coverage through games: each chapter lists its games; the coverage ledger has a game column; every skill-type row has a game or sandbox mission.
6. Games live in a DOM overlay outside the stage, pause the story, are reachable from a hub, from chapter break scenes and from checkpoint mini-breaks, remember progress (localStorage) and expose the mastery callback used by pathway mode.
7. Test the answers: a script plays every mission with the computed answers and must reach full stars; wrong-answer paths are exercised too.

## 9. Pathway mode (learn, pass the games as exams, checkpoint, next chapter)
Per chapter, in this order: (1) LEARN: summary slides generated from the scene notes (cheatsheet data) grouped by scene title, at most 4 entries per slide, plus a 'chapter in brief' slide from the recap; rule and formula slides show their plain-words box first; (2) GAMES: every game and sandbox of the chapter is passed like an exam (decks until a perfect round, sandboxes through their mission exam); a banner announces mastery with the stars and the next step; (3) CHECKPOINT: the chapter's questions, missed ones retried until all are right; passing opens the next chapter.
Rules: soft locks plus an 'Open everything' switch; the chapter index shows slides (seen ticks), games (mastered, stars) and checkpoint status; a global map of all chapters with a 'Continue here' button; the resume point is stored (localStorage) so the learner skips straight to where they stopped instead of repeating the chapter; story mode has a scene index per chapter with seen ticks and a 'Resume' on the start screen; storage keys are documented in the handoff. The overlay guards the stage's keyboard shortcuts (body class) and restores the pause state on close. Test: a script drives a small and a large chapter through learn, games and checkpoint to completion and checks that the next chapter unlocks.

## 10. Mock exam mode: a full 2-hour and a full 4-hour paper
- 2-hour paper = emulate the real exam: the real structure (parts, number of questions, weighting, total points, about 1.2 minutes per point), the real question forms (technical QCM, situation-based QCM, JSON/structure analysis, open questions, code writing, code comparison, parameter analysis, calculations, true/false...), a new scenario with new names and numbers, answerable from the guide. If a subject-full-guide mock exam exists, port it faithfully with its corrections.
- 4-hour paper = the anticipation paper: more patterns and questions the professor may ask that the 2-hour paper does not cover (other join/partition/consistency variants, traps, niche concepts, edge cases, every lab's first exercise as a situation question, multi-part case studies, more calculations and code), about twice the points. Build a coverage matrix (concept x form x paper) so every inventory row is tested in at least one paper.
- Question kinds: qcm, true/false, numeric fields (auto-checked with tolerance and list answers), written/code answers (textarea, then a model answer plus a marking list the learner ticks, giving a self-mark). Scenarios are shared by several questions.
- Answering flow on EVERY question: the learner chooses either 'Check my answer and show the correction' (verdict, points, answer, path, why the others fail, next time, where to revise with buttons that open the matching chapter) or 'Skip, come back later'. Looking at the correction without answering is recorded as 'looked', worth 0. Previous/Next, 'go to a skipped question', 'answer again'.
- Frame: hub with both papers (parts, points, status, optional clock), timer with pause (paused hides the question), progress bar, index grouped by part with status colours AND labels, finish-and-score at any time, results with total, a rule-of-three out of 20 (flagged as indicative), per-part bars, weak chapters, lists of skipped/wrong/looked questions, resume from localStorage, two-click 'start again' (no confirm() in sandboxed frames).
- Data: author the papers in a script (Python dicts) that asserts the points total, unique ids and valid answer indices, recomputes every numeric answer, and emits the JS data file; never hand-edit the generated file.
- Tests: a script plays each paper perfectly (score must equal the total, persists after reload), plays wrong and skipped paths, and runs the contrast audit on every exam screen in wide and tall.

## 11. Visual quality bar, voice and delivery
- Visual: characters/props with gradients, soft shadows, reacting eyes/expressions; a consistent icon set reused for the same concept everywhere; animated backgrounds with parallax decoration; sound effects (whoosh/ding/tick); camera shake only for emphasis. Replace placeholder rectangles with proper icons before shipping.
- Voice: always keep the browser-TTS fallback (and give the learner control over it: section 11b). For quality, after content freeze pre-render per-caption audio with a neural TTS (e.g. Kokoro-82M, offline), keep a JSON index keyed by a hash of the caption text, play via HTMLAudioElement, fall back to browser TTS on any miss, and make the scene wait for the audio to end plus a pause. Check file counts/sizes against artifact limits.
- Delivery: publish as an artifact (same file path on every update so the URL is kept, short label per version; do not paste the URL unless asked; the artifact copy has no doctype/html/head/body wrapper, starts with a <title> of two to four words and `:root{color-scheme:dark}`, and keeps the dark look as a deliberate single theme), send the standalone HTML and a zip of the project (src, exam data scripts, build and QA scripts, PROGRESS.md, HANDOFF.md; exclude screenshot folders, which can make the zip hundreds of MB). HANDOFF.md states: status per chapter and per mode, what is verified and what is not, pending fixes with exact code locations, QA tools and how to run them, kit cheat sheet, engine rules, storage keys. Publish a checkpoint version early and often so progress is never lost to a session limit. Never use rm with globs; write screenshots to fresh directories.

## 11b. Voice control (mandatory)
A 'Voice settings' panel (button in the control bar and on the start screen) with: a switch 'Read captions aloud'; a voice list from speechSynthesis.getVoices() (English voices first, then by language and name, 'online' marked for non-local voices, 'Browser default' first; refill the list on the voiceschanged event; a clear message when the device has no voices); sliders for speed 0.5-2 (default 1), pitch 0-2 and volume 0-1, each with a live value; 'Test voice' (speaks a sample sentence that contains subject terms), 'Stop', presets (slow and clear, normal, fast review) and 'Reset'. Choices apply immediately, test automatically after a change, and are saved with the progress (localStorage). ONE function (utter(text)) builds every utterance (story captions, exam correction replay, the test button): it applies the voice and its language, clamps rate, pitch and volume, and multiplies rate by the lesson Speed menu, so slowing one scene never loses the default. Spoken text still goes through the symbol-to-words cleaner. Test (wide and tall): inject fake voices, check the list order, select a voice, set rate, pitch and volume, press Test, and assert the utterance carries exactly those values; check persistence after reload, presets, reset, and that the lesson Speed multiplies.

## 12. Work loop and QA gates (all mandatory)
Per chapter: (1) write the scene plan from the inventory, listing the games, pathway slides and exam questions each row feeds; (2) code in stages (templates first, then custom scenes), build, run the error check; (3) run the gates, fix, re-run the failing gate, only then start the next chapter; (4) keep a task list (one task per chapter plus games, pathway, exams, audit, voice, publish) and send a one-line status about every 15 minutes.
G1 Build + runtime errors: load wide and tall, iterate every scene, capture console errors; zero allowed.
G2 Visual wide: screenshot every custom scene at >= 4 nominal times (early, mid-build, complete, final) at speed 1, SEQUENTIALLY (parallel browsers starve the animation clock), make a montage and LOOK at it (overlaps, touching boxes, clipping, text over art, slot-tag collisions, off-centre groups, unreadable sizes, empty half-screens, hidden elements).
G3 Visual tall: same, with the tall stage size, for every custom scene and a sample of template scenes.
G4 Automated overlap audit: OFF, OVERFLOW, COVERED, TEXTOVER; zero findings or each justified.
G5 Idle/dwell: no idle tail > 3 s; each caption's dwell >= readMs.
G6 Contrast/size audit: stage text sizes and contrast plus the DOM overlay contrast audit of section 4 (zero issues, wide and tall).
G7 Fact check: re-read each scene's captions, game answers and exam answers against the source; verify arithmetic by running it; mark examples.
G8 Coverage diff: ledger rows vs scenes vs checkpoint questions vs games vs exam questions; zero gaps; confirm every source document was mined (lab first exercises, hidden traps and niche concepts included).
G9 Chapter flow: play start to finish; pause/resume, next-chapter, notes panel, cheatsheet, checkpoint scoring.
