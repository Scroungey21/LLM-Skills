# Shorts variants and the retention-tuning loop (p10 + v8 condensation)

Both were built in the archived engine (`synthesis/shorts.py`, `synthesis/retention_tuner.py`, `api/analytics.py`, `api/tuning.py`, `synthesis/vertical_recap.py`). The tuner is the one piece of genuine statistics in the repo and its "tried and rejected" notes are the most valuable part - preserved below.

Contents: 1 Shorts as a niche variant - 2 Derived vertical recap (condensation) - 3 The `variant` invariant - 4 Retention-tuning loop - 5 What the replay world taught - 6 How to run a tuning cycle by hand - 7 Not built

## 1. Shorts as a niche variant (P10-REQ-1.x)

- A second, independent script `variant = "shorts"` can coexist with the `full` script for the same scored item. It runs through the *same* scriptwriter -> editor -> fact-check -> cue-validate sequence, fixed target **55 s** (`SHORTS_TARGET_RUNTIME_SECONDS`, deliberately not content-length-banded: a Short is scoped by attention span, not source richness; 55 s leaves margin under the ~60 s ceiling), hook-first.
- Generated by one direct synchronous call, **not** through the project step orchestrator (which stays `full`-only). A human approves it at Gate 1 like any script.
- **Rejected approach (P10-REQ-1.4):** deriving a Short by cutting the full script's synthesized audio - it produces audible mid-word/mid-breath seams and breaks the naturalness bar. Write a fresh compressed script and synthesize it. (Same rule as `news-explainer`: a Short is a rewrite, not a speed-up or excerpt.)
- CTA: `shorts_cta_style` is `link_to_full_video` (default; narrative niches) or `link_to_source` (intended for informational niches, "go read the details") - no seeded news niche actually sets it, so all fall to the default. The v8 engine's exact full-video sentence is "if you want more details, check the full video in the comments and description"; the live LITMUS channel uses its own constant (`SHORTS_CTA`, "... in the description") defined in `news-explainer` - **source A (engine) says "comments and description", source B (news-explainer, later live decision) says "description"; written as B for the LITMUS channel, A only for restored-engine side niches.** Code helper `ensure_shorts_cta` guarantees the final scene.
- Short structure (condensation prompt, V8): hook lands in the **first 2 seconds** on the single most surprising/consequential moment; **one** tight beat (state it, the one piece of context that makes it matter, the takeaway); **at most one** pattern-interrupt; every scene after the first `is_hook=false`; paraphrase and compress, never truncate mid-thought; no component/cues in cis mode.
- Per-niche Short advice (derived from the playbooks): cyber/ai-security - the consequence + the single removed barrier + what to do; infra - date, scale, trigger; autopsies/fraud - the finding and its attribution (sensitivity applies in full - a Short cannot drop the "alleged/found by" qualifier); myths - claim -> verdict word in the last second; retrospectives - the then-vs-now beat; weekly rundown - not a good Short source (use one segment as its own Short).

## 2. Derived vertical recap (V8)

- A 9:16 recap project spawned from an already-**Gate-2-approved** `cis` parent, linked by `derived_from_project_id`. It is a real project with its own raw/scored rows; the parent must be an original cis project (a derived project can never spawn another). It auto-completes scoring and asset curation by reusing the parent's approved assets, defaults to `automatic` + `gating_mode auto`, and its script is a **condensation** of the parent's narration (never a fresh independent write).
- Preflight before spending any LLM call: every screen type used must have a `9:16` entry in `aspect_ratio_variants` (the only seeded one is `atmosphere-narration`; all existing types were left null on purpose). A missing variant raises a named error. Method: before promising a vertical recap for a niche, check each screen type it uses has a vertical layout.

## 3. The `variant` invariant (P10 design section 2)

The orchestrator is `full`-only. Any query for a script by `scored_item_id` alone is a bug unless both variants are wanted (the unique index is `(scored_item_id, variant)`); persisting an assembled prompt to a pipeline step is `variant == "full"`-guarded (a Short shares its project with its full sibling and would clobber the full run's step display). With v11 supersession, lookups also filter `superseded_at IS NULL`.
Method equivalent: keep full and Short artifacts in sibling folders keyed by variant; a Short's run-log never overwrites the full's.

## 4. Retention-tuning loop (P10-REQ-3.x)

```
CSV import (YouTube Studio Advanced-mode export; operator-driven; no API capture)
 -> analytics rows  (+ the niche's scoring_weights AS THEY STOOD when the video was scored: scoring_weights_at_production)
 -> propose_tuning()  (PURE function over those rows; never mutates the niche)
 -> tuning proposal, status = pending
 -> named human reviewer approves  (reject leaves config untouched)
 -> niche.strategy_bundle.scoring_weights updated
 -> rendered into the scorer prompt on the next cycle ("Tuned scoring emphasis ... derived from this niche's own retention data")
```

- **CSV columns:** required `script_id`, `views`; optional `video_id`, `published_at`, `average_view_duration_seconds`, `average_view_percentage`, `ctr`, `retention_curve`.
- **Weights:** per-niche `dict[str, float]`, each in [0, 1]; the tuner's convention is five dimensions - `hook_density`, `pacing_variety`, `payoff_clarity`, `claim_density`, `engagement_bait`. No niche has tuned weights yet (nothing seeded).
- **Algorithm (what was built):**
  1. Only rows that recorded `scoring_weights_at_production` count; a row missing it contributes nothing. Need >= 2 usable rows overall and >= 2 per dimension (else that dimension gets no nudge).
  2. Outcome per row = 0.5 x z(average_view_percentage) + 0.5 x z(views) (views alone when the percentage is missing).
  3. Per dimension: Pearson r between that dimension's recorded weight and the outcome; raw step = r x 0.25 (`_HILL_CLIMB_STEP`, deliberately larger than any `max_delta` so `max_delta` is the binding safety rail).
  4. Clamp: `|new - current| <= max_delta` (required per-call argument; the replay world declared 0.15 so >= 7 passes are needed to cross the range, guaranteeing many human checkpoints) and `0 <= new <= 1`; record every clamped dimension.
  5. **Anti-slop diversity floor:** normalised Shannon entropy of |weights|; refuse the proposal (return current weights unchanged with an explanation) if entropy < **0.35**, or if entropy over `history + proposed` is monotonically non-increasing and has dropped by > **0.15** (slow multi-pass collapse). Chosen over silent capping because a refusal is a cleaner audit trail.
- **A first proposal needs explicit `current_weights`** (no prior approved baseline to default from).
- **Grading rule (P10-REQ-3.6):** grade a tuner by replay against a declared synthetic ground truth (a frozen scoring function + 50 rows, noise sigma 4.0, 5 buckets), requiring (a) it beats the static weights on retention and (b) it never leaves the declared bounds - never by comparing the tuner's output with itself.

## 5. What the replay world taught (keep as design lessons)

- **Rejected proxy:** mapping each rubric dimension to a slice of video runtime (retention curve at that slice's midpoint) was replayed and learned the wrong direction (`engagement_bait` nudged *up*): runtime position has no causal link to which weight was active when the *candidate article was selected*. The only sound attribution is the recorded weights-at-production. Do not reintroduce it.
- **Rejected model:** a joint ridge-regularised multivariate fit across all dimensions did *worse* than per-dimension correlation on the replay (net retention -17.1 vs +2.1; two wrong-signed dimensions instead of one) - ~50 correlated rows over 5 dimensions with no cross-validated regularisation is itself unstable. Future work only with cross-validation or more data.
- **Declared ground truth** (why single-dimension maximisation is wrong): hook_density saturating gain (22 x (1 - e^-3h)); broken-promise penalty (-10 x h x max(0, 0.4 - payoff)); pacing_variety interior optimum at **0.6**; payoff_clarity saturating gain (12 x sqrt(p)); claim_density interior optimum at **0.5**; engagement_bait strictly negative (-18 x b, plus -8 x h x b x (1 - pacing)) so its optimum is provably **0**. Analytic optimum: hook 1.0, pacing 0.6, payoff 1.0, claims 0.5, bait 0.0 (~94.9). Bucket means: near-optimal ~92.5, baseline ~75.1, axis-extreme ~71.4, random ~62.7, slop-trap ~46.5.
- **Operational deadlock (not a bug):** if every video between two approvals is scored under the same weights, there is zero variance and every correlation is 0 - no signal, no proposal. The tuner deliberately does not inject synthetic jitter (live experimentation is the owner's call). Practically: hand-adjust one dimension in separate approval cycles, produce a batch of videos under each variant, then propose.

## 6. How to run a tuning cycle by hand

1. After >= ~10 published videos per niche, export retention CSV rows, join each to the weights vector recorded when it was scored (write that into the run-log at scoring time - without it the data is useless).
2. Compute the per-dimension correlations and the clamped proposal as above (a small script is fine; it is arithmetic, not an LLM stage).
3. Show the proposal field-by-field to the owner (current -> proposed, clamped dims, entropy before/after). Only an explicit approval writes the new `scoring_weights` into the niche brief (new version file).
4. Re-score nothing retroactively; the new emphasis applies to the next candidates.

## 7. Not built / still open

- No console UI for analytics import or tuning review ever shipped (API only); no automated YouTube Analytics capture; Shorts had no dedicated trigger UI beyond the scripts list `variant` filter. Thumbnail generation and multi-language dubbing were out of scope for this wave (the news channel later adopted ComfyUI thumbnails separately).
- Real `analytics_snapshots` data never existed when the tuner was graded (only the synthetic replay), so the tuner is **unvalidated on real data**.
